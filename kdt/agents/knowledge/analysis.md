# 分析问题

- 只处理 RMVL/KDT 相关需求，先只读核对源码、已有组件和用例，不提交文件、不构建或执行测试。
- 分类为 `development`（组件与用例开发）、`design`（测试方案设计）、`consultation`（相关咨询）或 `out_of_scope`（无关请求，礼貌拒绝）。咨询只输出文字，不改文件。
- 用户通常提出最直接的需求，设计一切从简，但必须满足需求，不主动扩大范围。
- 不确定行为优先查历史设计方案，再按工程与底层机制上更合理的语义决策，不把现有 Adapter 或组件的错误当作规范。
- `session_summary` 为最多40词的精简短语，保留目标、API/工具名、必要版本约束，不复述过程。
- `acceptance_checks` 逐项列出本次新特性的可验证目标，如果有旧用例能完全代替的除外。例如 `lpss.tool` 的六项查询，应分别列出 node/topic/service 的 list/info，并按需求考虑 C++ 版本。
- 明确现状、直接需求与仍存疑的行为，不为尚未执行的验证编造结果。
